# ID Strategy

## Standard

All entity identifiers in Skild OS are **UUID v4** strings generated by
`newId()` in `src/core/ids/index.ts`.

## Why UUID v4

- Client-generated — works offline; no server round-trip to mint an ID.
- Sync-safe — no collisions when multiple devices create records offline.
- Portable — the same identifier survives migration from local storage to
  Supabase to a private server without remapping.
- Opaque — no information leakage (unlike sequential or timestamp IDs).

## Rules

- `newId()` is the ONLY sanctioned way to mint an ID. Modules must not call
  `Math.random()`, `Date.now()`, or bespoke schemes.
- IDs are treated as opaque `string`. Never parse them for meaning.
- Foreign keys use the same string type; there is no numeric ID variant.
- Test fixtures may hard-code UUIDs but should use the `newId()` helper for
  freshly created records so schema drift is caught.

## Fallback

Modern browsers and the Worker runtime both expose `crypto.randomUUID()`.
`newId()` falls back to a Math.random-based UUID v4 for legacy environments;
the format and version are preserved.
